# Каталог: что здесь лежит и зачем

Подробное описание всех 64 скиллов, 15 агентов и 8 workflow на русском.
Сами файлы написаны по-английски — это open-source проект, и английский нужен,
чтобы им пользовались и присылали правки.

Репозиторий: https://github.com/ibrohim1234567881717/game-dev-ai-skills

---

## Как это устроено в двух абзацах

**Скилл** — это папка с файлом `SKILL.md`: инструкция, которую ИИ-ассистент
подгружает не всегда, а только когда задача ей соответствует. При запуске он
видит лишь название и описание каждого скилла (~100 токенов), а полный текст
читает только при активации. Это и называется progressive disclosure: держать
под рукой сотню скиллов, платя контекстом за два-три нужных.

**Агент** — роль с ограничениями. Не «помощник вообще», а исполнитель с
запретами: агент `performance` не имеет права предлагать оптимизацию до
профилирования, агент `security` считает любого клиента враждебным,
`minecraft-specialist` отказывается писать код, пока не установлены loader,
версия игры и mappings. **Workflow** — процедура из шагов с чек-листом
готовности, доступная как slash-команда.

# ЧАСТЬ 1. СКИЛЛЫ ЯДРА (29)

Работают независимо от движка. Именно они несут метод, а платформенные скиллы
только уточняют его под конкретный движок через `uad-requires` — поэтому в
репозитории **ноль дублирования** (проверено: ни одной пары скиллов со
сходством текста выше 12%).

## Программирование (6)

| Скилл | Что делает |
|---|---|
| **software-architecture** | Границы модулей, направление зависимостей, что вынести в данные. Главный вопрос, который он заставляет задать: *что вероятно изменится?* — границы ставят туда. Запрещает спекулятивную абстракцию: если нельзя назвать, от чего защищает абстракция, её убирают. |
| **api-design** | Проектирование интерфейсов, которые потом нельзя менять безболезненно. Правило: сначала напиши код, которым API будут *пользоваться*, и только потом реализацию. Запрещает boolean-параметры, «тихие» ошибки и формат данных без поля версии. |
| **refactoring-safely** | Изменение структуры без изменения поведения. Жёсткое требование: сначала страховочная сетка (тесты либо характеризующие тесты), потом маленькие шаги с проверкой после каждого. Отдельно разделяет рефакторинг, переписывание и изменение поведения — их смешение и создало рефакторингу репутацию «ломающего всё». |
| **root-cause-debugging** | Поиск настоящей причины вместо гашения симптома. Правило: **нет исправления без доказанной причины**. Прямо запрещает добавить null-проверку в месте падения, проглотить исключение или вставить задержку. Требует, чтобы баг умели включать и выключать по команде — иначе причина не доказана. |
| **code-review-method** | Ревью, которое пытается сломать изменение, а не одобрить его. Отдельно рассчитан на код, сгенерированный ИИ: он *выглядит* правильным, поэтому правдоподобность запрещено принимать за доказательство. Самые сильные находки — отсутствия: нет теста, не обновлён вызывающий код, нет миграции. |
| **dependency-analysis** | Внутренние связи (циклы, связность) и внешние пакеты (версии, уязвимости, лицензии). Требует анализировать **lockfile**, а не диапазон в манифесте: вы аудируете то, что реально ставится. В игровых проектах считает зависимостями и ссылки на ассеты — одна жёсткая ссылка тянет в память всю цепочку. |

## Геймдев (5)

| Скилл | Что делает |
|---|---|
| **game-architecture** | Отделение симуляции от отображения — самое ценное структурное решение в игровом коде: правила, которые можно прогнать без рендера, тестируемы, переносимы на headless-сервер и переживут переписывание UI. Плюс выбор модели сущностей (наследование / композиция / ECS) и явный конечный автомат состояний игры вместо набора флагов. |
| **gameplay-systems** | Механики как система, а не как груда частных случаев. Характеристики = базовое значение + конвейер модификаторов, который **пересчитывается**, а не мутирует базу (мутация — причина классического бага «после баффа персонаж навсегда сильнее»). Способности — данные, а не ветки кода. |
| **input-systems** | Одна идея: игровой код реагирует на *действия*, а не на устройства. Без этого поддержка геймпада, переназначение клавиш и контексты ввода превращаются в переписывание. Явный стек контекстов вместо флагов чинит целый класс багов «меню открыто, а персонаж бежит». Плюс буферизация ввода — то, что отличает «отзывчивое управление» от «игра ест нажатия». |
| **save-systems** | Сохранения, которые переживут обновление. Две ошибки дают большую часть потерянного прогресса, и обе делаются рано и дёшево: **нет поля версии в формате** и **перезапись единственной копии при записи**. Требует атомарной записи через временный файл и миграций цепочкой `v1→v2→v3`, а не одного загрузчика с ветками на каждую историческую форму. |
| **multiplayer-networking** | Топология, авторитет сервера, клиентское предсказание и реконсиляция, компенсация задержки, бюджет трафика, обрывы связи. Главная мысль: авторитет проектируется с самого начала — прикрутить его потом это почти переписывание. Требует тестировать через симулятор сети (100–200 мс + потери), потому что игра, проверенная только по локальной сети, не проверена. |

## Графика (7)

| Скилл | Что делает |
|---|---|
| **rendering-fundamentals** | То, на что опирается вся остальная графика: линейное цветовое пространство, масштаб мира, экспозиция, порядок проходов кадра, физкорректные входы материалов, прозрачность и точность глубины. Большинство «неисправимых» проблем с картинкой — это нарушенный фундамент, а не баг. |
| **lighting-design** | Свет решает две задачи сразу: читаемость (куда идти, что важно) и настроение. При конфликте побеждает читаемость. Ключевой свет ставится первым, до всех остальных. Отдельно — выбор между запечённым и динамическим GI и стоимость теней. |
| **materials-and-shaders** | Входы PBR (альбедо, металличность, шероховатость, нормали), упаковка каналов, взрыв количества шейдерных вариантов, инстансы вместо уникальных материалов. Самая частая незамеченная ошибка — карта нормалей или шероховатости, импортированная как sRGB. |
| **vfx-and-particles** | Главная стоимость эффектов — не количество частиц, а **overdraw**: большие прозрачные квады слоями. Плюс читаемость на реальной дистанции камеры и на реальном фоне, а не крупным планом в пустой сцене. |
| **post-processing** | Тонмаппинг и экспозиция сначала, грейдинг последним. Прямо запрещает «чинить» плохой свет пост-обработкой: получается мутная картинка, которую всё равно придётся переделывать. Требует опции отключения motion blur и depth of field — для части игроков это вопрос физического комфорта. |
| **render-debugging** | Диагностика артефактов через изоляцию стадии кадра, а не через перебор настроек «пока не исчезнет». Таблица «симптом → класс причины»: розовая поверхность, чёрный объект, z-fighting, мерцание, ошибки сортировки прозрачности, shadow acne. |
| **level-design-and-environment** | Метрики персонажа фиксируются первыми, потом серый блокаут, и только потом арт. Окклюзия закладывается в планировку: длинные открытые линии обзора означают, что не отсекается ничего и уровень не влезет в бюджет. Проверка читаемости — на живом человеке, который уровня не видел. |

## Производительность (4)

| Скилл | Что делает |
|---|---|
| **performance-profiling-method** | Метод, на который ссылаются все остальные: `БАЗОВЫЙ ЗАМЕР → ПРОФИЛИРОВАНИЕ → ГЛАВНОЕ УЗКОЕ МЕСТО → ОДНО ИЗМЕНЕНИЕ → ПОВТОРНЫЙ ЗАМЕР`. Требует отчитываться во **времени кадра в мс, а не в FPS**: +10 FPS это 8.3 мс на 30 FPS и 0.6 мс на 120 — FPS скрывает правду. |
| **cpu-optimization** | Порядок действий, где каждый следующий шаг дороже предыдущего: убрать работу → починить сложность алгоритма → снизить частоту → сократить аллокации → улучшить доступ к памяти → вынести с критического пути → и только потом параллелить. |
| **gpu-optimization** | Определение класса стоимости через тест масштабированием разрешения: падает время — значит попиксельная стоимость (overdraw, сложность шейдера), не падает — пообъектная (draw calls, геометрия). Тени считаются отдельно: часто это самый дорогой проход. |
| **memory-optimization** | Разделяет три разные проблемы, которые постоянно путают: объём (слишком много резидентно), утечка (растёт и не возвращается) и churn (постоянные аллокации — это про время, а не про память). Требует cycle-тест: пройти уровни и вернуться в начало. |

## Продакшн (4)

| Скилл | Что делает |
|---|---|
| **testing-strategy** | Что тестировать, на каком уровне и что тест должен доказывать. Мера ценности теста одна: **упадёт ли он, если сломается описанное поведение?** Даёт два способа проверить слабый набор тестов — ручная мутация кода и рефакторинг без изменения поведения. |
| **bug-triage** | Превращение потока баг-репортов в приоритизированную очередь. Тяжесть определяется последствием, а не раздражением репортёра. Потеря данных — выше всего. Регрессии выше давних багов. «Не будем чинить» с указанной причиной — легитимный и нужный исход. |
| **version-control-workflow** | Git на проекте с гигабайтами бинарных ассетов: что коммитить в движковых проектах (`.meta`-файлы Unity — исходники, их потеря ломает все ссылки), LFS до первого большого коммита, блокировка файлов для несливаемых сцен. |
| **release-management** | Версионирование, воспроизводимость сборки, поэтапная раскатка, откат. Ключевое: сборка обязана сообщать свою версию и коммит, иначе краш-репорт игрока не сопоставить с исходниками. Релиз без возможности отката — это ставка, а не релиз. |

## Безопасность (3)

| Скилл | Что делает |
|---|---|
| **client-server-trust** | Базовое правило всей защиты: **клиент — это поверхность отрисовки и ввода, но никогда источник истины**. Сообщение клиента заявляет намерение, а не результат. Порядок валидации аргументов: тип → диапазон → существование ссылки → владение → легальность состояния → пересчёт бизнес-правила. |
| **threat-modeling** | Структурный разбор, что атакующий будет ломать и какие защиты окупаются. Без модели угроз защита строится равномерно, а значит впустую. Даёт STRIDE как перечень подсказок и требует записывать принятые риски с владельцем и датой. |
| **secure-coding** | Уровень реализации: инъекции (все они — одна и та же ошибка: значение попадает туда, где читается как синтаксис), обращение с секретами, безопасные значения по умолчанию, десериализация, гигиена зависимостей. |

## Roblox Studio (6)

| Скилл | Что делает |
|---|---|
| **roblox-security** | **Самый важный скилл всего репозитория.** Это не советы, а процедура аудита: инвентаризация всех RemoteEvent/RemoteFunction, классификация по последствиям, проверка авторитета сервера, валидация каждого аргумента, rate limiting, атомарность DataStore (именно неатомарные чтение-изменение-запись порождают дюп-эксплойты), идемпотентность `ProcessReceipt`. | **roblox-project-conventions** | Точка входа. Сервисы и DataModel, границы ServerScriptService/ReplicatedStorage, различие Rojo-проекта и проекта только в Studio — оно решает, применимы ли вообще правки файлов. |
| **roblox-client-server-architecture** | Дизайн границы, который проходит аудит `roblox-security`. Что реплицируется само (и добавлять туда remote — значит завести вторую копию состояния, которая разойдётся с первой), почему `RemoteFunction` с сервера на клиент блокируется на машине атакующего, и network ownership частей — обычное объяснение «в Studio физика работает, в живой игре ломается». |
| **roblox-datastore-persistence** | `UpdateAsync` вместо `SetAsync`, session locking, ретраи с backoff, `BindToClose`. Ключевая мысль: **дюп предметов почти никогда не баг магазина** — это неатомарное чтение-изменение-запись в хранилище. Чинить магазин бесполезно. |
| **roblox-monetization** | `ProcessReceipt` может быть вызван повторно для той же покупки — это не сбой, это контракт. Выдать до записи = дюп; записать до выдачи = игрок заплатил и не получил. Обе операции обязаны быть в одной атомарной записи. Скилл написан с той же строгостью, что и `roblox-security`: это скилл по безопасности, просто про деньги. |
| **roblox-luau-patterns** | Типизированный Luau (`--!strict`), экспортируемые типы, дженерики, идиоматичные модули, отличия Luau от Lua. |

| **web-frontend-architecture** | Границы компонентов, владение состоянием, клиентское против серверного состояния, стратегии рендеринга (CSR/SSR/SSG/streaming). |
| **web-backend-architecture** | Слои транспорт/сервис/данные, направление зависимостей, валидация на границе, конфигурация и секреты, статeless и горизонтальное масштабирование. |
| **web-typescript-patterns** | Настройки строгости, размеченные объединения, сужение типов, `unknown` вместо `any`, рантайм-валидация на границах против типов на этапе компиляции. |
| **web-css-layout** | Современная модель раскладки (flex/grid), адаптивность без хаков под устройства, слои каскада, токены дизайна, контейнерные запросы. |

# ЧАСТЬ 3. АГЕНТЫ (15)

## Основные (9)

| Агент | Ответственность и ограничения |
|---|---|
| **orchestrator** | Точка входа. Сам почти не пишет код: определяет проект и версию, выбирает скиллы, разбивает работу, делегирует, собирает результат и запускает независимое ревью. Правило: **определить до того, как решать**. Не спрашивает пользователя о том, что написано в файлах проекта. |
| **architect** | Проектирование до реализации. Обязан проверить дизайн на трёх вероятных будущих изменениях — это то, что отличает проект от рисунка. Сопротивляется спекулятивной обобщённости: требует показать второй реальный случай, прежде чем вводить абстракцию. |
| **programmer** | Реализация. Сначала — версия платформы из файлов проекта, потом — чтение окружающего кода, чтобы совпасть по стилю. Запрещены заглушки и `TODO` вместо кода. Обязан запустить сборку и тесты либо явно сказать, что не смог. |
| **debugger** | Диагностика. Нет исправления без доказанной причины. Прямо перечислено, что запрещено: null-проверка в месте падения, `try/catch` вокруг проблемы, задержка «чтобы не гонка». Честный ответ «причина не найдена, вот что исключено» ценнее спекулятивного фикса. |
| **reviewer** | Независимый враждебный проход. Существует именно потому, что код от языковой модели **читается правдоподобно вне зависимости от корректности**. Проверяет, а не узнаёт: запускает тесты, прослеживает реальный путь исполнения с конкретными значениями, ищет отсутствия. |
| **qa** | Проверка того, что работа действительно работает. Определяющее ограничение: сообщает то, что **наблюдал**, а не то, что должно происходить. Отдельно проверяет миграцию сохранённых данных со старой версии. |
| **performance** | Не имеет права предложить оптимизацию до профилирования. Если профилировать невозможно — выдаёт ранжированный список гипотез, явно помеченных как гипотезы. |
| **graphics** | Сначала устанавливает render pipeline, потому что графические советы не переносимы. Порядок работы: свет → материалы → пост-обработка. Не описывает картинку, которую не видел. |
| **security** | Аудит по границе доверия. Ранжирует по реальной ценности для атакующего, а не по интересности техники. Не производит эксплойт-инструменты — только находки, шаги воспроизведения для владельца системы и исправления. Обязан указывать, что **не** проверял. |

## Платформенные (6)

Каждый загружает свой пак скиллов и держит дисциплину версий своего движка.

| Агент | Ключевое ограничение |
|---|---|
| **unreal-specialist** | Читает `EngineAssociation`; понимает, что GUID = сборка из исходников. Помнит, что сырой указатель на UObject без `UPROPERTY` — висячий указатель. |
| **unity-specialist** | Устанавливает **две** вещи: версию редактора и render pipeline. Знает, что Unity сериализует поля, а не свойства, и не сериализует словари и интерфейсы. |
| **godot-specialist** | Определяет мажорную версию по `config_version` и никогда не смешивает API Godot 3 и Godot 4 (таблица различий встроена в описание агента). |
| **roblox-specialist** | Сначала выясняет: Rojo-проект или только Studio — от этого зависит, применимы ли правки файлов вообще. Клиент считается враждебным по умолчанию. |
| **minecraft-specialist** | **Отказывается писать код**, пока не установлены loader, версия и mappings. Честен насчёт устаревания сигнатур: учит форме решения и способу найти актуальный API, вместо уверенных выдумок. |
| **web-specialist** | Читает версии из **lockfile**, а не из диапазонов манифеста. Использует команды из `scripts` проекта, а не запомненные. |

# ЧАСТЬ 4. WORKFLOW (8)

Доступны как slash-команды после установки.

| Команда | Процедура |
|---|---|
| **/build-feature** | ПОНЯТЬ → ОСМОТРЕТЬ ПРОЕКТ → ОПРЕДЕЛИТЬ СТЕК → ЗАГРУЗИТЬ СКИЛЛЫ → СПРОЕКТИРОВАТЬ → РЕАЛИЗОВАТЬ → ПРОТЕСТИРОВАТЬ → ОТРЕВЬЮИТЬ |
| **/fix-bug** | ВОСПРОИЗВЕСТИ → СОБРАТЬ УЛИКИ → СУЗИТЬ ПОИСК → ДОКАЗАТЬ ПРИЧИНУ → ИСПРАВИТЬ → РЕГРЕССИОННЫЙ ТЕСТ. Тест обязан падать на неисправленном коде — это проверяется. |
| **/optimize** | БАЗОВЫЙ ЗАМЕР → ПРОФИЛИРОВАНИЕ → УЗКОЕ МЕСТО → ОДНО ИЗМЕНЕНИЕ → ПОВТОРНЫЙ ЗАМЕР → СРАВНЕНИЕ |
| **/review** | Враждебное ревью: проверить заявления, сверить версию, целенаправленно охотиться на классы дефектов, проследить реальный путь, ранжировать находки. |
| **/prototype** | Ответ на **один** вопрос одноразовым кодом. Явно снимает планку качества и требует потом выбросить результат или переписать заново. |
| **/graphics-pass** | ФУНДАМЕНТ → СВЕТ → МАТЕРИАЛЫ → ПОСТ-ОБРАБОТКА → ЗАМЕР. Порядок и есть смысл: грейдинг плохо освещённой сцены придётся переделывать. |
| **/security-review** | Определить область → карта границы доверия → инвентаризация пересечений → авторитет → валидация → атомарность хранения → ранжирование находок. |
| **/release-check** | Сборка из чистого клона → тесты → бюджеты → **миграция сохранённых данных** → безопасность → требования площадки → возможность отката → решение GO/NO-GO. |

# ЧАСТЬ 5. ИНСТРУМЕНТЫ

Python 3.9+, **без единой зависимости** (свой парсер YAML в комплекте).

```bash
python tools/uad.py detect .            # что это за проект и какой версии
python tools/uad.py select "запрос"     # какие скиллы загрузятся, а какие нет
python tools/uad.py validate --strict   # проверка репозитория
python tools/uad.py install --target claude-code --platforms godot web
python tools/uad.py doctor              # состояние окружения
```

**108 тестов:** детекция 23, сценарии 19, точность выбора 19, валидация 19,
установка 14, парсер YAML 14. Валидатор имеет собственные негативные тесты,
доказывающие, что он действительно отвергает каждый класс дефектов — валидатор,
который не умеет падать, хуже отсутствия валидатора.

# ЧАСТЬ 6. ЧЕСТНЫЕ ПРОБЕЛЫ
